Summary decision at a glance

Problem
New links cannot expire: POST /links ignores an expiry field and GET /:code redirects while the process lives.
Decision
Accept optional integer expiresInSeconds from 1 through 2,592,000; retain URL-only calls, store a UTC deadline in the existing Map, and delete lazily with 404 not found at the cutoff. Return expiresAt only for finite links; use Cache-Control: no-store on their 302 responses.
Verify by
Exercise both API paths against a real server: 201 for an expiring link, 302 before the deadline, 404 at/after it; check the 30-day bound, invalid inputs, legacy redirects, response headers, and loss of links after process restart.

Context facts before design

The current handler stores only normalized URLs and returns {"code":"…"} (F1); a supplied one-second expiry was observed to have no effect (F6). Resolution redirects without a deadline check or cache directive (F2). The state is already volatile across process restarts (F3), and the only documented creation client is the API (F4). New finite redirects need a no-store directive for compliant caches, but that cannot revoke redirects cached before deployment (F7).

Micro features one API contract, two behaviours

  1. M1

    Creation: the API caller optionally requests a link lifetime of 1–2,592,000 seconds.

    depends on existing POST /links · size S · omitted expiry preserves the old response

  2. M2

    Resolution: a finite link redirects only before its stored cutoff.

    depends on M1 recording an epoch deadline · size S · expired entries are deleted on lookup

Interpretation for review

Q1-C specifies the duration and cap but not the finite 201 response body. This proposal keeps the Explore page's finite-link expiresAt field (E2), calculated as a UTC ISO timestamp. ADR acceptance includes that interpretation; it does not change URL-only responses.

Decisions accepted · 2026-10-01

  1. D1

    On POST /links, normalize the URL first; if expiresInSeconds is present, require a JSON integer in [1, 2,592,000]. Sample Date.now() once, set deadlineMs = now + seconds × 1000, and return 201 with {"code":"…","expiresAt":"…Z"}. If omitted, return only {"code":"…"}; malformed duration returns 400 bad expiry without storing a code.

    F1, F5, Q1, and Q2 require a bounded, opt-in extension. Rejected the 365-day limit (Q1-A), absolute client timestamp (Q1-B), and changing URL-only replies (Q2-B/C). A previously ignored but invalid expiry field will now fail explicitly.

    M1 · deadline stored as epoch milliseconds, response formatted with toISOString(); bad URL still wins over bad expiry

  2. D2

    Keep one process-local Map whose values hold the normalized URL and an optional deadline; check the deadline on each GET and delete an expired entry only when looked up. No timer, database, or migration.

    Q4 accepts volatility described by F3. Choose O1 over periodic sweeping (O2) and persistent storage (O3): a timer cannot replace per-GET enforcement, while persistence would add deployment work not requested.

    M1 + M2 · no restart durability; unvisited expired entries stay resident

  3. D3

    On GET, an unknown or expired code returns the existing 404 not found without the target URL; an expired code is removed. A finite code redirects with the original 302 Location only while Date.now() < deadlineMs, with Cache-Control: no-store. A code without a deadline retains its original 302 and headers.

    Q3 rejects 410 with tombstones (Q3-B); Q2 preserves old clients (F2). F7 warrants no-store only for finite redirects so cooperating caches recheck the origin. Previously cached 302s cannot be recalled.

    M2 · at the cutoff the original target is never served again by this entry

  4. D4

    Expose expiry only through the existing JSON API; document the optional field, 30-day bound, finite response, 404 cutoff, restart limit, and no-store header in README.

    Q5 selects API-only: no UI or identity exists (F4). Reject the form proposed by Q5-B; no auth or front-end deployment is added.

    M1 · caller-facing contract, not a new endpoint

Consequences trade-offs, rollout, rollback

Accepted trade-offs

The Map loses all links after restart; unvisited expired entries stay resident. Server wall-clock jumps can move the effective cutoff, and previously cached redirects can outlive the new no-store header. No background cleanup, persistence, or clock synchronization is added (D2, D3).

Collision and visibility boundary

The existing six-character code generator can overwrite a live entry on collision (F8); this ADR does not change the generator. Anyone who can call the unauthenticated API can create finite links, as today. HTTP statuses and the finite 201 timestamp make the change externally observable; there is no new telemetry pipeline.

Rollout / rollback

Deploy server.js, tests, and README together; no persisted schema or migration. A rollback restores the prior handler and restarts the volatile process, losing in-memory links; no compatibility shim or feature flag is needed. Existing URL-only clients continue to receive the same 201 and 302 contracts when running the new version.

Out of scope: a browser form, creator identity, restart durability, periodic sweeping, collision repair, and revoking redirects cached before deployment. Accept this ADR before building.
