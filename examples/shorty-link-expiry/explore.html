Summary the question

Problem
POST /links creates a short code, but a supplied expiry is ignored; while the process stays up, GET /:code redirects indefinitely. The creator needs to choose when a newly created code stops redirecting without breaking existing URL-only clients.
Why now
Creator-selected expiry is the requested change; no incident or external deadline is documented in this repository.
Leaning
Accept an optional, bounded duration at creation, store its deadline with the URL, check on every GET, return the existing 404 after expiry, and mark expiring redirects Cache-Control: no-store. Keep the current in-memory lifetime unless you need links to survive a restart.

Options same expiry contract, different storage

Each option validates the creator's requested deadline, checks it again on every GET, and uses no-store on an expiring link's 302. They differ in how deadlines survive and when abandoned entries are reclaimed.

O1

In-memory deadline; lazy deletion

leaning
  • Fits the single-process Map; no new dependencies.
  • Deadline checked at resolution, not subject to timer scheduling.
  • A restart erases active links; unvisited expired entries remain in memory.
  • Multi-process deployment would have inconsistent links.
Effort SRisk medium: volatile
O2

In-memory deadline; periodic sweep

alternative
  • Reclaims expired entries even if no visitor returns.
  • Keeps the existing storage model.
  • Still loses active links on restart; adds a timer and repeated scans.
  • GET must check the cutoff too: a late sweep cannot enforce expiry.
Effort MRisk medium: volatile
O3

Persistent deadline store

alternative
  • With stable shared storage, active links and deadlines can survive process restarts.
  • Possible to garbage-collect expired rows independently.
  • Adds a database/file, schema, operational ownership, and deployment changes.
  • Single shared instance and backups matter if serving on multiple hosts.
Effort LRisk medium: migration

Risks and unknowns decide before building

Reliability is not permanence

F3: the current Map loses every link on restart. If a creator expects a link to work until its chosen expiry, choose O3; otherwise the chosen time is only an upper bound while this server process remains alive.

Cache and clock limits

F7: new no-store responses do not revoke an already-cached 302 or force a noncompliant cache. An inaccurate server wall clock also shifts an absolute cutoff; duration input avoids client timezone parsing, not server clock drift.

Unvisited entries and collisions

O1 only reclaims an expired Map entry when its code is requested; there is no bound on unvisited entries today. The existing six-hex-character generator overwrites an older link on collision (F8); fixing that separate existing risk is not assumed here.

Scope boundary

No login or front end exists (F4). “Creator” currently means the caller of POST /links; a visual creation form would be a third micro feature only if you choose it.

Questions for you pick one option for each

Q1How should the caller choose the expiry time?

Controls API shape, timezone interpretation, validation limits, and the exact UTC cutoff returned in the 201 response.

Q2What happens when the creator omits expiry?

Existing callers send URL only (F1); changing their lifetime is a compatibility change.

Q3What should an expired code return?

404 preserves the existing not-found contract; 410 tells consumers the link once existed but requires retaining that distinction.

Q4Must a link remain usable through a server restart until its expiry?

Determines whether the existing volatile Map is sufficient and whether abandoned expired entries need background cleanup.

Q5Where does the creator set expiry?

There is no web UI today (F4); adding one changes the scope and introduces a third micro feature.
