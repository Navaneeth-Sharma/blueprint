Summary accepted decision

Problem
POST /links always generates a code; callers cannot claim a memorable short path. An alias must not replace an existing redirect, including a generated code.
Decision
Accept an optional alias on the existing POST. Validate it strictly, reserve links, reject taken names with 409, and retry generated codes that collide. Both kinds remain in the same process-local map.
Verify by
Exercise create, redirect, invalid inputs, duplicate claims and restart against the HTTP server; force a generated-code collision in an allocator test. Both kinds of link must return 404 after restart.

Context

The existing API returns 201 {"code":"…"} for a generated six-hex code, ignores supplied aliases, and resolves GET paths from one map (F1, F3). Generated writes currently skip an occupancy check, so merely adding alias writes would risk changing an existing redirect (F2). The route spelling links overlaps the API path, and callers have neither authentication nor a form (F4, F5). Existing tests cover ordinary redirect and invalid target URL, not claims or collisions (F6).

Decisions

  1. D1

    Keep POST /links: omitted alias uses a new six-character hex code; supplied valid alias becomes code. Success is 201 with only {"code":"…"}, and GET /<code> redirects exactly as today.

    Preserves old callers (F1) and uses the existing GET map lookup. Choose O1; reject the separate PUT endpoint O2 as unnecessary API surface.

    Q1 → A · unchanged URL parsing and 400 bad url precede alias handling

  2. D2

    A present alias must be a string matching ^[a-z0-9-]{1,32}$ and must not equal links. No trim, coercion, case folding or decoding; invalid input returns 400 bad alias without storing a key.

    GET looks up the exact path (F4); a strict spelling avoids ambiguous or competing representations. An omitted field alone selects the generated branch; null and empty string are invalid.

    Q2 → A · rejects Q2 → B's mixed-case/underscore/64-character rule

  3. D3

    Use one map namespace: check for an occupied alias before storing; return 409 alias taken for any prior key regardless of URL. For generated codes, draw again while the candidate is occupied, then store only an unused key.

    Both creation paths must preserve earlier redirects (F2). Keep the check and insertion contiguous without async work in one Node process so two claims cannot both succeed. Reject returning an existing name on identical URL (Q3 → B): a claim is never an idempotent replay.

    Q3 → A · Q5 → A · this is process-local, not a cross-process uniqueness guarantee

  4. D4

    Keep aliases and generated links in the existing process-local Map, with no expiry until process reset and no persistence across restart or sharing between processes.

    Matches current storage (F3); reject Q4 → B's durable multi-process store as beyond the chosen lifetime.

    Q4 → A · no migration or rollout dependency

  5. D5

    Retain current unauthenticated POST access. Any caller may claim a free alias; expose no browser form, account ownership, editing or deletion API.

    There is no authentication or UI to extend (F5). Reject Q5 → B authentication and Q6 → B browser form; the first claim controls redirects only until the process store resets.

    Q5 → A · Q6 → A · name squatting is an accepted risk

Consequences

Accepted claim risk

Unauthenticated callers can squat on names; no ownership, release or edit operation exists. A restart releases all names and invalidates every redirect, including generated links (D4, D5).

Capacity and visibility

Generated codes retain a six-hex, 16,777,216-value space. Retrying collisions preserves existing redirects but availability degrades as it fills; no production metrics or logs exist today (F5). Verify creation and redirect by HTTP; capacity management is outside this API-only change.

Rollout and rollback

No migration or deployment dependency. Deploying the modified process resets its Map, as any restart does today; rollback reverts the handler and likewise resets all process-local links. Communicate that no persisted claim survives either action.

Out of scope

Authentication, a browser form, cross-process uniqueness, persistent storage, edit/delete APIs, URL-scheme policy changes, and new telemetry.
