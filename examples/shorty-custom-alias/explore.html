Summary explore

Problem
Callers can shorten a URL but cannot choose the short path: POST /links ignores an alias field and always generates a six-character code. An alias must not replace an existing redirect, including one generated for another caller.
Why now
The requested change is to let people choose a memorable alias. This repository has an HTTP API, no browser interface, and no persistent link store.
Leaning
Add an optional alias to the existing request and return it in the existing code field; reject conflicting or invalid claims. Keep current storage and API-only scope unless Q4 or Q6 changes it.

Micro features explore

  1. M1

    Claim a chosen short path through the shortening API; redirect from it without disturbing generated links.

    Scope: request contract, alias validation, conflict and generated-code collision handling, GET lookup · Depends on: existing in-memory links Map · Size: S if API-only and in-memory. A browser form or durable storage would expand scope (Q4, Q6).

Current state explore

Findings explore

  1. F1

    POST /links parses only url, always generates a six-character lowercase hexadecimal code, and returns 201 {"code":"…"}. In a live probe, supplying "alias":"team" still returned a random code; GET /team returned 404.

    server.js:9–23 · live POST /links and GET /team probe · high confidence
  2. F2

    The generated code is written with links.set without checking whether a key already exists. A future custom alias such as abcdef could be overwritten by a generated collision unless generation checks the same namespace.

    server.js:20–22 · high confidence for overwrite path; collision is a possible event, not observed
  3. F3

    Both creation and redirects use one module-level Map. Links disappear on process restart and are not shared across independently running processes.

    server.js:6, 20–29, 34–37 · high confidence from implementation
  4. F4

    GET uses the request path after the leading slash as the exact map key. POST /links is method-specific, so links is not currently a generated code but overlaps the API path in spelling.

    server.js:9, 26–31 · high confidence
  5. F5

    Malformed target URLs get 400 bad url; misses get 404 not found. No authentication, database, logs, or browser form appears in the checked-in API and test files.

    server.js:1–37 · README.md:1–7 · test/server.test.js:1–29 · high confidence for checked-in surfaces
  6. F6

    Existing tests exercise an ordinary POST→GET redirect and bad target URL, but not name conflicts, format boundaries, or concurrent claims.

    test/server.test.js:12–29 · high confidence

Options explore

O1

Optional alias on POST /links

leaning
  • Same endpoint and response shape; existing callers omit the new field.
  • GET /<alias> already uses a path key; no new redirect route.
  • Creation is not idempotent by default; duplicate names need an explicit response policy.
  • Still inherits process-local storage unless Q4 changes it.
Effort SRisk medium: collisions
O2

Separate PUT /links/:alias claim

alternative
  • Separates chosen names from random-code requests.
  • Alias is visible in the request path and may suit clients using PUT.
  • A second creation route, plus parsing and documentation for both routes.
  • Still needs validation, ownership policy, atomic conflicts, and generated-code protection.
Effort MRisk medium: API complexity

Risks and unknowns explore

Availability and ownership

An unauthenticated, global first-claim rule lets anyone reserve short names, including brands. There is no account or editing mechanism today; Q5 determines whether that remains acceptable.

Lifetime

The current Map loses both random and chosen codes on restart, and a second process has a different Map (F3). Promising durable aliases needs a durable store and atomic uniqueness for all codes, not only a new request field (Q4).

Existing redirect safety

Simply adding links.set(alias, url) would allow a caller to replace somebody else's redirect. Generated codes must also avoid existing alias keys (F2). Current target-URL scheme validation is unchanged by this proposal.

Operational visibility

No app-level logging or metrics exist in the checked-in server (F5). A creation→redirect smoke check can notice broken alias resolution; there is no production signal for name-claim failures yet.

Questions for you explore · decision gate

Q1How should callers send an alias?

Defines the creation contract while preserving existing clients (F1).

Q2Which alias spellings and limits should work?

Path keys currently match exactly (F4); spelling and route reservation affect links people share.

Q3What should happen when a requested alias already exists?

Changing an existing redirect is unsafe; this chooses duplicate-claim semantics. Generated-code collisions must avoid existing keys under either answer (F2).

Q4Should links outlive a restart?

All current links are in memory (F3); persistent aliases alone would give random links different lifetimes.

Q5Who may claim an alias?

The current endpoint is unauthenticated (F5); public claiming permits name squatting.

Q6Is a browser form needed?

The repository currently contains only an HTTP API (F5). A form would add a separate UI micro feature.
