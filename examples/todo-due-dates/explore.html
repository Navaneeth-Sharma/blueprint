Summary

Problem
A todo item is only an id, a title and a done flag, so nothing says when it's due. todo list prints items in id order, which means late items are mixed in with everything else.
Why now
You asked for it. The change is small: the store is schemaless JSON and nothing reads unknown keys (F1, F4), so there is no migration.
Leaning
O1: an optional ISO date string "due" on each item, set with todo add <title> --due YYYY-MM-DD. list works out which items are overdue when it prints and puts them first. No new files, no dependencies, no migration.

Micro features

  1. M1

    todo add <title> --due YYYY-MM-DD stores an optional due date, and todo list shows it after the title

    depends on nothing · size S · todo/cli.py only

  2. M2

    todo list prints open items whose due date has passed first, labelled overdue. Everything else keeps its current order.

    depends on M1 · size S · todo/cli.py only

  3. M3

    Optional: set or clear the due date on an item that already exists (todo due <id> <date|none>)

    depends on M1 · size S · only if Q6 → B

Findings

  1. F1

    Items are a JSON list of {id, title, done} dicts in one file, $TODO_FILE or ~/.todo.store. There is no schema version. load reads the whole file and save rewrites it.

    todo/store.py:7-17 · high confidence
  2. F2

    list prints every item, done ones included, in file order. Since add appends, that is also id order. The line format is f"{id:>3} [{mark}] {title}".

    todo/cli.py:31-34 · todo/cli.py:18-19 · high confidence
  3. F3

    add takes one positional title. parse_args runs before store.load(). So an argparse type= converter that rejects a value exits with code 2 and a usage error, and the file is never touched.

    todo/cli.py:11-16 · high confidence
  4. F4

    The code reads only id, title and done. It never checks for other keys. So the current version ignores a new "due" key, and rolling back to it keeps working on a store file that has due dates.

    todo/cli.py:18-34 · high confidence
  5. F5

    date.fromisoformat as an argparse type accepts 2026-10-05 and rejects 2026-13-01, 2027-02-29, 10/05/2026, "" and " 2026-10-05" with exit 2 and todo add: error: argument --due: invalid fromisoformat value: '…'. On 3.11 and later it also accepts 20261005 and week dates like 2026-W40-1 (read as 2026-09-28).

    ran here on Python 3.12.10 · docs.python.org/3/library/datetime.html#datetime.date.fromisoformat · high confidence
  6. F6

    Zero-padded YYYY-MM-DD strings sort in date order, so a stored due date can be compared as a string with date.today().isoformat(). That breaks for hand-edited values: "2026-9-5" < "2026-10-01" is False.

    ran here · high confidence
  7. F7

    The tests call cli.main(argv) in-process, with TODO_FILE pointed at a temp file. Nothing lets a test choose what "today" is, so overdue tests either patch the date source with unittest.mock or use dates far in the past and future.

    tests/test_cli.py:11-25 · high confidence
  8. F8

    done is the only command that changes an existing item. There is no edit. Without a new command, the only way to give an existing item a due date is to re-add it.

    todo/cli.py:10-13, 22-30 · high confidence
  9. F9

    The repo declares no minimum Python version (no pyproject, no setup.py). This machine runs 3.12.10.

    git ls-files · python3 --version · high confidence

Options

O1

Optional "due" ISO date on each item, overdue worked out when listing

leaning
  • One file changes (cli.py). No migration: old items just have no key (F1).
  • Rolling back is safe, because the old code ignores the key (F4)
  • Overdue can never go stale, because it is never stored
  • Overdue depends on the machine's local date and time zone
  • The list output changes, which matters to anyone who parses it
Effort SRisk low
O2

Store a datetime or timestamp instead of a date

not leaning
  • Allows "due at 17:00"
  • Needs time zones, a clock format and more parsing
  • No one asked for a time of day
Effort MRisk medium
O3

Versioned store with a migration, plus a stored overdue flag

not leaning
  • An explicit schema for later fields
  • A migration step and rollback work for one optional key
  • A stored flag goes stale at midnight
Effort MRisk medium

Risks and unknowns

Risk

todo list output changes: lines can move to the top and gain a suffix. Anyone piping it through grep or awk will notice. Items without a due date keep exactly today's line, and nothing moves unless something is overdue (E15).

Unknown

There is no Python floor (F9). On 3.11 and later --due quietly accepts 20261005 and week dates (E5). Stored values are always in normal form, so the file is the same on every version.

Out of scope

store.save is a non-atomic write_text, so a crash or two concurrent adds can lose data. That is true today, and this change doesn't make it worse.

Questions for you

Q1When is an item overdue?

Decides whether something due today jumps to the top of the list (E12).

Q2What order does todo list use?

Overdue items come first either way. This decides the order inside that group and whether the rest of the list changes (E14).

Q3How should due dates and overdue items look?

This is the visible part of the change and the line format people might parse.

Q4Which date formats does --due accept?

Shortcuts are quicker to type, but each one is parsing code we own and have to test (F5).

Q5Can you add an item whose due date has already passed?

Lets you record something you're already late on, but it also lets a typo in the year through (E7).

Q6Can you set or clear the due date on an item that already exists?

If not, the only way to give an existing item a due date is to re-add it (F8). Choosing B adds M3.
