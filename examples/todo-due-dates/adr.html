Summary

Problem
A todo item has no due date, and todo list prints everything in id order, so late items are mixed in with the rest (F2).
Decision
todo add <title> --due YYYY-MM-DD stores an optional "due" ISO date on the item. todo list works out overdue items when it prints: open items due today or earlier, shown first, oldest due date first, with (due …, overdue) after the title. One file changes (todo/cli.py). No migration, no dependencies.
Verify by
python3 -m unittest discover tests, then the real CLI against a temp TODO_FILE: add items due yesterday, today and tomorrow plus a done item due in the past, run list, and check the order, the suffixes and that the store file is byte-identical afterwards. Repeat list under two TZ values for E17.

Context

Items are a schemaless JSON list of {id, title, done} in one file, and the code reads only those three keys, so a new optional key needs no migration and survives a rollback (F1, F4). argparse runs before store.load(), so a bad --due is rejected with exit 2 before the file is touched (F3), and date.fromisoformat already does the parsing and validation (F5). Stored strings can't be trusted for comparison once someone hand-edits the file (F6), so overdue is decided on parsed dates. The tests drive cli.main(argv) in-process with no clock hook (F7).

Decisions

  1. D1

    add takes an optional --due with type=date.fromisoformat. When given, the item gets "due": due.isoformat(). When not given, the item has no due key at all, exactly as today.

    Parsing happens in argparse, so every bad value exits 2 before the store is loaded (F3). Storing isoformat() means 20261005 is saved as "2026-10-05" and the file looks the same on every Python version (F5). No check against today, so a past date is allowed (Q5). Rejected O2 (datetime: time zones and a clock format nobody asked for) and O3 (versioned store and migration for one optional key).

    Q4 → A · Q5 → A · consequence: old items and rollback need nothing (E8, E9)

  2. D2

    An item is overdue when it is not done and its stored due parses with date.fromisoformat to a date on or before date.today(). list reads today once per run. Overdue is never stored.

    Comparing parsed dates, not raw strings, keeps hand-edited values like "2026-9-5" from sorting wrongly (F6). A value that raises ValueError or TypeError counts as undated. Today is the machine's local date. Tests build their dates from date.today() plus or minus a day, so no clock hook is added (F7).

    Q1 → B · consequence: an item due today is labelled overdue (see Consequences)

  3. D3

    list prints overdue items first, sorted by (due date, id), then every other item in file order, which is id order.

    Only the overdue group moves, so a list with nothing overdue keeps its current order (E15). Sorting affects printing only: list never calls save, and ids stay as they are (E16).

    Q2 → A

  4. D4

    Items with a truthy due value get the suffix (due <value>), or (due <value>, overdue) when overdue, after today's line f"{id:>3} [{mark}] {title}". Items without a due date print exactly today's line.

    Plain text, no colour, no new mark column. An unparseable value is printed as it is stored, so the user can see and fix it (E10). null and "" get no suffix (E18).

    Q3 → A

  5. D5

    No command to set or clear a due date on an existing item. M3 is dropped.

    The only way to change a due date is to re-add the item (F8). Add todo due <id> <date|none> later if that gets annoying.

    Q6 → A

Consequences

Trade-off: “overdue” on the day it's due

With Q1 → B, an item due today prints (due 2026-10-01, overdue) on 2026-10-01. That's the chosen rule, but the word is strict. If it reads wrong once you use it, the fix is one comparison (<= → <) or a due today label; say so before build.

Output change

todo list lines can move to the top and gain a suffix, which matters to anyone piping it through grep or awk. Undated items keep today's exact line, and nothing moves unless something is overdue (E15).

Rollout

One commit to todo/cli.py, its tests and the README. No migration: existing store files work unchanged (E8).

Rollback

Revert the commit. The old code ignores due keys and keeps them when it saves (E9), so re-applying later loses nothing.

Out of scope

Editing due dates on existing items (D5), relative dates like tomorrow (Q4 B), colour (Q3 C), a Python version floor (F9), and the non-atomic store.save, which can lose data on a crash or concurrent write today and is not made worse here.
