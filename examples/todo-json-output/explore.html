Summary

Problem
todo list prints padded text with no escaping, so scripts have to scrape columns. A title that contains a newline creates a fake row (F2), and ids of 1000 or more shift the columns (F3).
Why now
Shell scripts need to read the list reliably. Today the only other way is to read ~/.todo.store directly, and that file is internal storage that nothing documents (F5).
Leaning
O1: todo list --json prints json.dumps(items), a compact JSON array of {id, title, done}. Output without the flag stays byte-for-byte the same. About 3 lines of code plus one test.

Micro features

  1. M1

    todo list --json writes every item to stdout as JSON and exits 0.

    depends on nothing · size S · one file (todo/cli.py) plus a test and a README line

One micro featureThis is a small change, so there is only M1 and the tables below have no M# column. If you pick Q4 B or C, add/done output becomes M2.

Current state

Findings

  1. F1

    The plain format is f"{item['id']:>3} [{mark}] {item['title']}", printed once per item. Titles are not escaped or quoted.

    todo/cli.py:32–34 · high confidence
  2. F2

    A title containing \n prints as several lines. todo add $'line one\n 9 [x] forged' produced a line exactly like a real finished item 9. Parsing the text output is unsafe, not just fragile.

    ran it: python3 -m todo list | od -c · high confidence
  3. F3

    The id column is padded to width 3. Id 1000 prints as 1000 [ ] big, so scripts that cut fixed columns break, while scripts that split on whitespace keep working.

    todo/cli.py:34 · ran it · high confidence
  4. F4

    The store already holds the target shape: a JSON array of {"id": int, "title": str, "done": bool}. It is written with json.dumps(indent=2), which by default escapes non-ASCII as é. add is the only thing that creates items, so every item has exactly these three keys.

    todo/store.py:13,17 · todo/cli.py:19 · high confidence
  5. F5

    A script could run jq . ~/.todo.store today. That ties it to the storage path ($TODO_FILE or ~/.todo.store) and the storage format, and neither is documented: the README lists only the three commands.

    todo/store.py:1,8 · README.md:5–7 · high confidence
  6. F6

    The list subparser takes no arguments. Both todo list --json and todo --json list exit 2 today with error: unrecognized arguments: --json. That lets a script tell an old version from a new one.

    todo/cli.py:12 · ran it · high confidence
  7. F7

    If the store file is zero bytes or corrupt, store.load() raises JSONDecodeError: a traceback on stderr, exit 1, nothing on stdout. Every command goes through this path. save() is a plain write_text, not atomic, so a reader running during a write could see a partly written file.

    todo/store.py:13,17 · ran it · high confidence
  8. F8

    The tests already capture stdout and the exit code (run_cli), and one test pins the plain format [x] buy milk. A --json test fits next to it. No new dependency is needed: the stdlib json module covers it (Python 3.12), and jq is at /usr/bin/jq for manual checks.

    tests/test_cli.py:21–32 · high confidence

Options

O1

--json → JSON array

leaning
  • One line: print(json.dumps(items))
  • Escaping fixes F2 and F3
  • Same shape as the store (F4), and jq '.[]' works on it directly
  • The output shape is tied to the store shape, so new store fields show up in the output
  • You need jq or similar to read it in shell
Effort SRisk low
O2

--json → JSON Lines

alternative
  • One object per line: while read -r and grep work on it
  • Streams well for long lists
  • An empty list prints nothing, which looks like a failure unless the script checks the exit code
  • Not what people usually expect from a flag named --json
Effort SRisk low
O3

--format text|json

alternative
  • Leaves room for csv or tsv later
  • Speculative: nobody has asked for a second format
  • More to type, plus a choices check
Effort SRisk low
O4

--porcelain tab-separated

alternative
  • No jq needed: IFS=$'\t' read -r id done title
  • A tab or newline in a title still breaks it unless we invent and document escaping rules, so it brings back F2
Effort SRisk medium

Risks and unknowns

Contract

Once scripts depend on --json, its shape is a public contract. With Q2 A, any field added to the store later shows up in the output too. Adding fields is safe for jq users; renaming or removing one would break them.

Existing, not new

save() is not atomic and a corrupt store ends in a traceback (F7). Scripts that poll list --json will hit this more often than a person typing commands would. Fixing it is a separate change unless Q5 B pulls part of it in.

Unknown

Whether the scripts that will consume this can rely on jq. If they can't, JSON Lines (O2) or tab-separated output (O4) matter more.

Questions for you

Q1What shape should --json output have?

This is the contract scripts will depend on. Hard to change once it ships.

Q2Which fields does each item carry?

Decides whether the output follows the store or stays fixed if the store gains fields (F4).

Q3How should the JSON be formatted?

Affects how it reads in a terminal and how it behaves when stdout isn't UTF-8 (E5). jq reads all three.

Q4Which commands get --json?

Scope. add already prints just the new id, which scripts can read as is.

Q5What should happen when the store is corrupt?

Scripts already get exit 1 and an empty stdout. The only question is whether stderr is a traceback or one readable line (F7).
