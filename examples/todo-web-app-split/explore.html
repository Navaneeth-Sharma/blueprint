Summary

Problem
todo is a one-person CLI that rewrites a single JSON file on every command. You want it to become a web app where several people have accounts, share lists, and get an email when something is due.
Why now
You asked for it. The JSON store has no locking (F1), so a web server would lose writes as soon as two requests overlap. The storage change comes first whatever else is decided.
Leaning
Flask and SQLite on one small VM (O2). Sign-in by emailed link. Lists shared by email address. One daily digest email sent by a cron job running todo remind over plain SMTP. Split into three records, one per shippable release (Q1).

Micro features

  1. M1

    SQLite store. One database file replaces ~/.todo.store, with tables users, lists, list_members and items. The CLI keeps add, list and done on top of it, and a new todo import copies an old JSON file in.

    depends on — · size M

  2. M2

    Web UI for one list. Server-rendered pages to see, add and complete items in a browser. Forms use POST, then redirect back to the list.

    depends on M1 · size M

  3. M3

    Accounts. Sign in (method per Q4), a session cookie, and sign out. Every list belongs to a user, and anyone else gets a 404.

    depends on M2 · size M (L with passwords)

  4. M4

    Shared lists. A user can have several lists and share one with an email address. Members add and complete items. Only the owner deletes the list or removes members.

    depends on M3 · size M

  5. M5

    Due dates. An optional due date on each item, set with a date input on the web or --due in the CLI. Items are shown as due today or overdue in the viewer's time zone.

    depends on M1 (M2 for the UI) · size S

  6. M6

    Email reminders. todo remind, run by cron, sends each user at most one digest a day of their undone items that are due or overdue. Safe to run twice, and logs one line per run.

    depends on M4 M5 · size M

Current state

Findings

  1. F1

    The store reads the whole JSON file and writes the whole list back on every write, with no lock and no atomic rename. A crash during write_text can leave a truncated file, and two concurrent writers lose one update.

    todo/store.py:11-17 · high confidence
  2. F2

    An item is {id, title, done}, and ids are max(id) + 1. There is no owner, list, due date or delete command, and titles are not validated (an empty string is accepted).

    todo/cli.py:11-19 · high confidence
  3. F3

    All the logic lives inside main(), mixed with print. A web layer can't reuse add, done or list until they are pulled out into store functions.

    todo/cli.py:16-35 · high confidence
  4. F4

    There are two unittest tests that drive cli.main against a temporary TODO_FILE. Both pass today (Ran 2 tests … OK). They are the regression net for keeping the CLI working.

    tests/test_cli.py:10-35 · ran 2026-10-01 · high confidence
  5. F5

    The project has no packaging and no dependencies (no pyproject.toml or requirements.txt). Locally: Python 3.12.10, SQLite 3.49.1, sqlite3.threadsafety == 3, hashlib.scrypt available on OpenSSL 3.0.16, and Flask not installed.

    git ls-files · local python3 check · high confidence
  6. F6

    Both stdlib servers carry a production warning: http.server "is not recommended for production", and wsgiref "is a reference implementation and is not recommended for production". The cgi module was removed in 3.13, so form parsing falls to urllib.parse.

    http.server · wsgiref · PEP 594 · high confidence
  7. F7

    In WAL mode, SQLite readers and the writer don't block each other, but "there can only be one writer at a time". Python's sqlite3.connect(timeout=5.0) is the busy wait. Connections are tied to their thread by default (check_same_thread=True), so the web app should open one connection per request.

    sqlite.org/wal · sqlite3 docs · high confidence
  8. F8

    Flask 3.1.3 (2026-02-18) needs Python 3.9 or later and pulls in Werkzeug, Jinja2, MarkupSafe, itsdangerous, click and blinker. Its session cookie is signed, not encrypted, and Flask has no built-in CSRF protection.

    PyPI Flask · Flask security docs · high confidence (medium on "no CSRF")
  9. F9

    If we store passwords (Q4 B or C), OWASP ranks Argon2id first and scrypt second. The minimum for scrypt is N=217, r=8, p=1, and for PBKDF2-HMAC-SHA256 it is 600,000 iterations. hashlib.scrypt is in the stdlib on every supported Python.

    OWASP Password Storage · high confidence
  10. F10

    OWASP treats SameSite as defence in depth, not a replacement for a CSRF token. Use a synchronizer token (or a signed double-submit cookie), and never change state on a GET, which Lax does not cover. The recommended cookie is __Host- prefixed, Secure and HttpOnly.

    OWASP CSRF · OWASP Sessions · high confidence
  11. F11

    smtplib and EmailMessage are stdlib, and RFC 8314 prefers implicit TLS on port 465. Postmark, SES, Resend and Mailgun all offer SMTP relay as well as an HTTP API. Gmail requires SPF or DKIM from every sender, and DMARC plus one-click unsubscribe above 5,000 messages a day (the unsubscribe rule is for "marketing and subscribed" mail).

    RFC 8314 · Resend SMTP · Gmail sender rules · high confidence (medium on whether reminders count as "subscribed")
  12. F12

    zoneinfo has been in the stdlib since 3.9 (Windows also needs the tzdata package). cron's DST handling is only defined for jobs at a fixed time. A job that runs every 15 minutes and computes each user's local date itself sidesteps that.

    zoneinfo · cron(8) · high confidence
  13. F13

    A scheduler inside the web process runs once per worker. The APScheduler FAQ warns that sharing jobs across processes leads to "duplicate execution or… missing jobs". An external cron with a database uniqueness key avoids both.

    APScheduler FAQ · high confidence (medium that it applies to plain thread loops)

Options

O1

Stdlib only

considered
  • Zero dependencies, same as today (F5)
  • WSGI app plus sqlite3, hashlib.scrypt, smtplib and zoneinfo, all built in
  • We would hand-roll routing, HTML escaping, sessions and CSRF, all of it at the trust boundary
  • The stdlib servers are not for production (F6), so a server such as waitress is needed anyway
Effort MRisk medium
O2

Flask + sqlite3 + cron

leaning
  • Jinja autoescaping and signed session cookies come built in
  • store.py stays the data layer for both the CLI and the web (F3)
  • Reminders are one more CLI command that cron runs
  • First dependency, and it needs packaging
  • CSRF tokens and schema migrations are ours to write (about 30 lines)
Effort MRisk low
O3

Django

considered
  • Auth, sessions, CSRF, migrations, admin and send_mail all come built in
  • The least security code we write ourselves
  • Rewrites store.py as ORM models, and the CLI becomes manage.py commands
  • The project skeleton alone is bigger than today's app
Effort MRisk low

Risks and unknowns

Risk

The whole security surface is new: sessions, CSRF, output escaping, and sending email to addresses users type in. Framework defaults matter more here than line count, which is why the leaning is not stdlib only.

Risk

Deliverability. Without SPF, DKIM and DMARC on the sending domain, Gmail and Yahoo will send reminders to spam or reject them (F11). This needs a domain you control plus an SMTP account. Unknown: do you have both?

Risk

Sign-in links. Corporate mail scanners open links in emails. If a GET consumed the token, those users could never sign in, so the token has to be consumed on a POST (E11). This is a known pattern; I couldn't check a source for it in this session.

Unknown

How many users? The leaning assumes tens of users on one box, where SQLite's one-writer-at-a-time limit never matters (F7). A public service with thousands of users changes Q2 and Q9.

Risk

On a single box, the SQLite file is the entire state. The ADR needs a nightly sqlite3 todo.db ".backup …" and a restore that has been tested.

Questions for you

Q1One record, or split it?

There are six micro features. Each release below is usable on its own, and the email decisions shouldn't hold up M1.

Q2Where will it run?

This decides the database and the scheduler. SQLite and cron both assume one machine with a persistent disk.

Q3Which web stack?

This sets how much security plumbing (escaping, sessions, CSRF) we write ourselves (O1–O3, F8).

Q4How do people sign in?

Emailed links replace three flows (password storage, reset and email verification) with one, but every sign-in waits on email.

Q5How does sharing work?

This decides whether sharing sends email (a spam vector) and whether it reveals which addresses have accounts.

Q6What does a reminder look like?

This sets the email volume, whether due dates need a time, and how simple it is to guarantee no duplicates.

Q7How is email sent?

This is the one outside dependency on the path of both sign-in and reminders. Every listed provider accepts SMTP (F11).

Q8What happens to the CLI and existing data?

The two existing tests and anyone's current ~/.todo.store depend on this (F4).

Q9Who can create an account?

Open sign-up turns the app into a public email sender, which needs rate limits and abuse monitoring.
