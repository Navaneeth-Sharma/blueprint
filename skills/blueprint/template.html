Summary every sheet

Sample sheetEvery Blueprint component, filled with one example change. The tag on each heading names the phases that use it.

Problem
The provider retries webhooks for up to 3 days. Our handler has no idempotency check, so a retry after a lost 200 applies the credit twice. This happened twice in September.
Decision
Gate every event on its provider event id with a Redis SET NX before enqueueing. A unique index on the ledger stays as the backstop.
Verify by
Replay one captured event 50 times in parallel. Expect one ledger row, one 200 marked new and 49 replays.

Micro features every sheet

  1. M1

    A retried or duplicated webhook applies its credit exactly once

    depends on nothing · size S

Findings explore

  1. F1

    The provider retries with exponential backoff for up to 72 hours and can deliver the same event twice at once.

    Provider webhook docs, "Retries" · high confidence
  2. F2

    The handler enqueues before any check. The worker inserts into ledger_entries, which has no unique constraint on the event id.

    handlers/payments.py:88 · workers/credit.py:41 · high confidence
  3. F3

    Both duplicate-credit incidents started with 502s from the load balancer during a deploy, which the provider treats as failures and retries.

    INC-231, INC-244 · medium confidence

Decisions decide

  
    
    
  1. D1
    Dedupe on the provider event id at ingest, before enqueue, with SET evt:{id} NX EX 259200.
    Concurrent deliveries are real (F1), so the check must be atomic. Chose O1; O2 still repeats emails.
    TTL from Q2 → A (assumed)

  2. D2
    Fail closed on Redis errors: return 503 with Retry-After: 30.
    A delayed credit is recoverable. A double credit needs a manual reversal.
    Q1 → A
    3. 
    
  3. D3
    Add a unique index on ledger_entries(provider_event_id). The worker treats a conflict as success.
    Covers keys that expire before a very late retry, and any Redis data loss.

Consequences decide · build

  
Risk
Redis becomes a hard dependency of ingest. An outage delays every payment webhook until it recovers.

  
Assumed
Q2 had no answer. Took the recommended option A: event ids are kept for 72 hours.

  
Rollback
Remove the gate behind WEBHOOK_DEDUPE=0. The unique index stays; it is safe on its own.
